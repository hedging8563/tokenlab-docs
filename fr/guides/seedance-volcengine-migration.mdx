Ce guide s’adresse aux applications qui envoient déjà des requêtes Seedance au format Volcengine. Vous pouvez conserver les noms d’Action, `Version=2024-01-01`, `content[]`, les corps PascalCase des ressources et l’enveloppe de réponse Volcengine. Seuls le point de terminaison et l’authentification doivent changer.

## Ce qui change

| Élément | Client Volcengine existant | TokenLab |
| --- | --- | --- |
| URL de base | `Volcengine API` | `https://api.tokenlab.sh/` |
| Authentification | `AK/SK` | `Authorization: Bearer <TOKENLAB_API_KEY>` |
| Requête Action | `Action`, `Version` | `Action`, `Version` |
| Corps de tâche | `content[]` | `content[]` |
| Corps de ressource | `PascalCase` | `PascalCase` |
| Résultat asynchrone | `ID de tâche` | `cgt-...` + Polling |

Les requêtes contenant uniquement une signature AK/SK renvoient `401 AuthenticationError`. Les clients Action peuvent utiliser `POST /?Action=...&Version=2024-01-01` ; `POST /api/v3?Action=...&Version=2024-01-01` reste disponible. Les clients REST utilisent `/api/v3/contents/generations/tasks`.

## Format des requêtes et cycle de vie des tâches

Si votre intégration envoie déjà des requêtes Seedance de style Volc, vous pouvez utiliser le point de terminaison compatible au lieu de remodeler le body pour `/v1/videos/generations`. Envoyez votre clé API TokenLab avec `Authorization: Bearer ...`, utilisez `POST /api/v3/contents/generations/tasks` pour la création REST ou `/api/v3?Action=CreateContentsGenerationsTasks&Version=2024-01-01` pour les requêtes Action. La création retourne un ID `cgt-...`; les statuts utilisent `queued`, `running`, `succeeded`, `failed`, `cancelled` ou `expired`.

Ce point de terminaison accepte les éléments `content[]` comme `text`, `image_url`, `video_url`, `audio_url` et `draft_task`. `callback_url` reçoit le même objet de requête à chaque passage à `queued`, `running`, `succeeded`, `failed` ou `expired` ; `succeeded` et `failed` sont réessayés jusqu’à trois fois après cinq secondes. Conservez l’interrogation comme solution de repli.

Ne réutilisez pas la structure de réponse de `/v1/tasks/{id}` pour v3. v1 utilise `pending`, `processing`, `completed` et `failed` ; v3 utilise `queued`, `running`, `succeeded`, `failed`, `cancelled` et `expired`. En v3, `duration` est une chaîne et `error` n’apparaît qu’en cas d’échec.

Pour reprendre après une déconnexion, envoyez un `Idempotency-Key` unique avec la création REST. Le même body et la même clé renvoient le même ID `cgt-...` ; un body différent avec la même clé renvoie `409`.

## Actions de tâche

| Action | Élément | JSON |
| --- | --- | --- |
| `CreateContentsGenerationsTasks` | Créer une tâche vidéo | `model`, `content[]` |
| `GetContentsGenerationsTask` | Lire une tâche | `TaskId` |
| `ListContentsGenerationsTasks` | Lister les tâches | Filtres, pagination |
| `DeleteContentsGenerationsTasks` | Annuler ou supprimer une tâche | `TaskId` |

## Exemple REST minimal

```bash
curl 'https://api.tokenlab.sh/api/v3/contents/generations/tasks' \
  -H "Authorization: Bearer $TOKENLAB_API_KEY" \
  -H "Idempotency-Key: $CLIENT_JOB_ID" \
  -H "Content-Type: application/json" \
  -d '{
    "model":"seedance-2.0",
    "content":[
      {"type":"text","text":"A cinematic product reveal"},
      {"type":"image_url","role":"reference_image","image_url":{"url":"https://example.com/reference.png"}}
    ],
    "ratio":"16:9",
    "duration":5,
    "resolution":"720p"
  }'
```

## Liste de contrôle de migration

1. Remplacez l’hôte API par `https://api.tokenlab.sh`.
2. Remplacez la signature AK/SK par une clé API Bearer TokenLab.
3. Conservez l’Action, la version et la casse du corps existants.
4. Utilisez le même `ProjectName` pour les requêtes associées de ressources et de vérification.
5. Enregistrez les identifiants de tâche, de groupe et de ressource renvoyés par TokenLab.
6. Validez une création, un polling, une liste et une erreur avant de déplacer le trafic de production.
